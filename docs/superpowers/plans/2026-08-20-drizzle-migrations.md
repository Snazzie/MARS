# Drizzle Migration Adoption Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans (recommended). Steps use checkbox (`- [ ]`) syntax and are executed task-by-task.

**Goal:** Move future PostgreSQL schema migrations from the custom migration array to Drizzle Kit while preserving existing data, schema names, tagged-SQL queries, and deployed migration history.

**Architecture:** Freeze the current nine custom migrations as a legacy compatibility boundary. Add a Drizzle schema declaration and checked-in migration directory. A bridge runs legacy migrations only as needed, validates the boundary, initializes Drizzle metadata, and then delegates all post-boundary migrations to Drizzle's PostgreSQL migrator.

**Tech Stack:** Bun 1.2.20, TypeScript, PostgreSQL, `postgres`, `drizzle-orm`, `drizzle-kit`, Bun tests.

## Global Constraints

- Do not rewrite existing tagged-SQL queries.
- Do not rename tables, columns, indexes, environment variables, or storage paths.
- Do not extend the custom migration array after the legacy boundary.
- Existing legacy migration checksums must be validated before the Drizzle baseline is marked applied.
- Fresh and existing databases must converge to the same schema.
- Migration failures must fail startup and preserve transactional consistency.
- Skip formatters, linters, and project-wide test suites during individual implementation tasks; run the complete verification gate once at the end.

## File Map

- Modify `packages/db/package.json`: add Drizzle dependencies and migration scripts.
- Create `packages/db/drizzle.config.ts`: Drizzle Kit PostgreSQL configuration.
- Create `packages/db/src/drizzle-schema.ts`: declarations matching the existing schema.
- Create `packages/db/src/migrations/0000_legacy_baseline.sql`: reviewed baseline SQL for fresh installs.
- Create `packages/db/src/migrations/0001_post_baseline.sql`: first Drizzle-owned migration marker/example with no schema change if no pending product migration exists.
- Create `packages/db/src/migrations/meta/_journal.json` and snapshot metadata generated by Drizzle Kit.
- Create `packages/db/src/migrate.ts`: legacy bridge plus Drizzle migrator entry point.
- Modify `packages/db/src/index.ts`: export the new migration entry point and preserve existing exports.
- Modify `apps/control-plane/src/index.ts`: call the new migration entry point.
- Create `packages/db/src/migrate.test.ts`: migration bridge and idempotence tests.
- Modify `packages/db/src/schema.test.ts`: assert fresh schema/migration compatibility where existing fixtures require it.
- Modify `IMPLEMENTATION-STATUS.md`: document migration ownership and the frozen legacy boundary.

### Task 3: Implement the legacy bridge and Drizzle migration runner

**Files:**
- Create: `packages/db/src/migrate.ts`
- Modify: `packages/db/src/index.ts`
- Modify: `apps/control-plane/src/index.ts`
- Test: `packages/db/src/migrate.test.ts`

**Interfaces:**
- Export `migrateDatabase(sql: DatabaseClient): Promise<void>`.
- `migrateDatabase` preserves the existing advisory lock and applies legacy versions 1–9 only when needed.
- After legacy version 9 is verified, it initializes Drizzle migration metadata and applies post-baseline migrations.

- [ ] **Step 1: Extract legacy migration definitions without extending them**

Move the current migration list/checksum compatibility logic behind the new migration module. Keep the known legacy checksum exceptions. Do not add version 10 to the custom list.

- [ ] **Step 2: Implement bridge validation**

Under the advisory lock, create/read `schema_migrations`, apply missing legacy migrations, validate every applied legacy checksum, and require version 9 before proceeding. Fail with a specific migration-boundary error if history is missing or mismatched.

- [ ] **Step 3: Initialize Drizzle metadata safely**

Use Drizzle's migration metadata format and migration runner for fresh databases. For an existing version-9 database, insert the exact Drizzle baseline metadata only after the legacy boundary validation succeeds. Make the bridge idempotent and transaction-safe.

- [ ] **Step 4: Delegate post-boundary migrations to Drizzle**

Run the checked-in Drizzle migration directory through Drizzle's PostgreSQL migrator. Do not split SQL on semicolons in the Drizzle-owned path.

- [ ] **Step 5: Change production startup to the new entry point**

Replace the `migrate(db)` call in `apps/control-plane/src/index.ts` with `migrateDatabase(db)`. Preserve the existing database client and all query modules.

- [ ] **Step 6: Add failure and idempotence tests**

Cover fresh initialization, existing version-9 upgrade, repeated startup, checksum mismatch, incomplete legacy history, and a Drizzle-owned migration failure. Assert failures reject startup and do not record a successful migration.

- [ ] **Step 7: Run focused migration tests**

```bash
bun test packages/db/src/migrate.test.ts packages/db/src/schema.test.ts
```

Expected: PASS.
