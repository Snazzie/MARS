# GitHub Actions cache interception plan

## Context
Whitesmith should transparently replace GitHub Actions cache service v2 for ordinary `actions/cache@v5` and cache-enabled first-party setup actions, without workflow edits, and persist cache archives through either an S3-compatible API or the control-plane host filesystem. The selected first release uses Whitesmith-hosted upload/download URLs rather than Azure-looking hostnames: uploads still implement the Azure block-blob calls that cache v2 forces, while downloads use the toolkit's compatible non-Azure HTTP path and therefore do not receive Azure-hostname concurrent-download optimization. Implement the feature in the existing TypeScript/Bun services only—no new .NET code, dependency, service, runner fork, or runner patch; the official GitHub runner remains unchanged.

## Approach
1. **Define the cache bootstrap contract and keep disabled deployments on GitHub cache.**
   - In `packages/contracts/src/orchestration.ts`, add strict `CacheProxyConfig = { cacheBaseUrl: z.string().url(), resultsHost: z.string().min(1) }` and optional `cacheProxy: CacheProxyConfig.optional()` to `LeaseBootstrapEnvelope`; export the inferred type. Extend `apps/orchestrator/src/runtime.ts:Lease` with the same optional property.
   - `WHITESMITH_CACHE_STORAGE` accepts exactly `off`, `local`, or `s3` and defaults to `off`. `apps/control-plane/src/cache/config.ts` returns `undefined` for `off`; otherwise it validates all cache settings at startup and exposes `{ storage, publicBaseUrl, resultsHost, tokenIssuer, jwksUrl, retentionDays, maxBytesPerRepository }`. Use `PUBLIC_BASE_URL` for `publicBaseUrl`, default `resultsHost` to `results-receiver.actions.githubusercontent.com`, token issuer to `https://token.actions.githubusercontent.com`, retention to 7 days, and per-repository capacity to 10 GiB. Invalid or incomplete enabled configuration is a startup error, not a silent fallback.
   - In `apps/control-plane/src/job-reconciler.ts:runQueuedJobReconciliation`, attach `{ cacheBaseUrl: PUBLIC_BASE_URL origin, resultsHost }` to the encrypted lease envelope only when cache is enabled. Do not place storage credentials, the GitHub runtime token, or certificate private material in the envelope.

2. **Add immutable cache metadata and bounded lifecycle to PostgreSQL.**
   - Add migration version 10 in `packages/db/src/index.ts` and its SQL in `packages/db/src/schema.ts` for `action_cache_entries` and `action_cache_parts`. `action_cache_entries` contains UUID `id`, internal `organization_id`/`repository_id` foreign keys, numeric `github_repository_id`, `scope`, `cache_key`, `version`, `state` (`uploading`, `blob_ready`, `ready`, `deleting`), opaque UUID-derived `object_key`, nullable backend multipart ID, byte size, created/updated/last-accessed timestamps, and upload expiry. Enforce one immutable row per `(github_repository_id, scope, cache_key, version)` and index ready-entry lookup by repository, scope, version, key, and recency. `action_cache_parts` is keyed by `(entry_id, block_id)`, also uniquely constrains `(entry_id, part_number)`, and stores the decoded 1-based part number, size, and nullable S3 ETag.
   - Create `packages/db/src/action-cache.ts` and export it from `packages/db/src/index.ts`. Provide atomic functions `reserveCacheEntry`, `recordCachePart`, `markCacheBlobReady`, `finalizeCacheEntry`, `findCacheEntry`, `markCacheEntriesForDeletion`, and `deleteCacheEntryMetadata`. `reserveCacheEntry` resolves `github_repository_id` through `dashboard_repositories`, rejects unavailable/unknown repositories, and returns `null` on the immutable-key conflict. `findCacheEntry` searches token scopes in permission-descending order: exact primary key first, then primary-prefix newest-first, then each restore key in caller order as exact then prefix newest-first; all matches require identical repository ID and version and `state='ready'`.
   - Escape PostgreSQL `LIKE` metacharacters in prefix keys. Accept cache keys of 1–512 UTF-8 characters, versions of 1–128 characters, at most 10 restore keys, and scopes of 1–1024 characters. Treat `size_bytes` as a decimal int64 string or safe integer and reject negative/overflowing values.
   - Extend `apps/control-plane/src/retention.ts` with cache cleanup orchestration rather than deleting metadata alone: abort `uploading`/`blob_ready` entries older than one hour; delete ready entries idle longer than `WHITESMITH_RETENTION_CACHE_DAYS`; after each finalize, evict least-recently-used ready entries until the repository total is at most `WHITESMITH_CACHE_MAX_BYTES_PER_REPOSITORY`. Mark rows `deleting`, delete backend objects/multipart uploads, then delete metadata; leave `deleting` rows for retry when backend deletion fails. A download grant updates `last_accessed_at`, and cleanup excludes grants issued in the prior 15 minutes so a freshly returned signed URL is not removed in flight.

3. **Implement one streaming storage contract with local and S3 backends.**
   - Add `apps/control-plane/src/cache/storage.ts` with `CacheStorage` methods `beginUpload(entry)`, `putPart(entry, part)`, `completeUpload(entry, orderedParts)`, `abortUpload(entry)`, `statObject(objectKey)`, `createDownload(objectKey, expiresAt)`, and `deleteObject(objectKey)`. Request bodies and downloads remain streams; never materialize an archive or 64 MiB block into a single JavaScript buffer.
   - Add `apps/control-plane/src/cache/local-storage.ts`. Store only UUID-derived paths under `${WHITESMITH_CACHE_LOCAL_ROOT ?? DATA_ROOT + '/cache'}`; never derive a path from repository, scope, key, version, query text, or block ID. Write concurrent blocks to entry-specific temporary files with exclusive creation. On block-list commit, concatenate the declared block order through streams into a same-filesystem temporary archive, fsync, atomically rename to the final object, and delete part files; a one-block upload may rename directly. `createDownload` returns a signed control-plane URL and the download route supports `GET`, `HEAD`, and one RFC 7233 byte range with `206`, `Content-Range`, `Accept-Ranges`, and exact `Content-Length`.
   - Add `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` to `apps/control-plane/package.json`, then add `apps/control-plane/src/cache/s3-storage.ts`. Configure `S3Client` from `WHITESMITH_CACHE_S3_BUCKET`, optional `WHITESMITH_CACHE_S3_ENDPOINT`, `WHITESMITH_CACHE_S3_REGION` (default `us-east-1`), `WHITESMITH_CACHE_S3_FORCE_PATH_STYLE`, and the standard `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optional `AWS_SESSION_TOKEN`. Map begin/part/commit/abort to `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, and `AbortMultipartUpload`; return a 15-minute presigned `GetObject` URL for downloads. Validate enabled local storage with a create/write/delete probe and S3 with `HeadBucket` during startup.
   - Decode the two block-ID layouts used by GitHub's Azure client ecosystem: a 48-byte decoded ID with the decimal zero-based index after byte 36, and a 64-byte decoded ID with the big-endian uint32 index at byte 16. Convert to S3 part number `index + 1`, enforce 1–10,000, reject duplicate part numbers with different block IDs, and require the committed `<Latest>` list to contain contiguous indices `0..n-1` in order. The first-party clients already emit that ordering; rejecting noncontiguous/reordered lists keeps local concatenation and S3 multipart assembly byte-identical without a second S3 copy.

4. **Serve cache v2 control and data APIs with repository-scoped authentication.**
   - Add `apps/control-plane/src/cache/auth.ts`. Reuse the existing `jose` dependency and a cached remote JWKS to verify the original `Authorization: Bearer` GitHub runtime JWT signature and exact issuer. Parse the `repository_id` string claim and the `ac` JSON claim as a non-empty array of `{ Scope: string, Permission: integer }`; permission 1 may read and permission 2 may read/write. Never trust repository or scope metadata from the Twirp body over verified token claims.
   - Add `apps/control-plane/src/cache/grants.ts` using the existing `SecretBox` to encrypt and authenticate 15-minute `{ operation: 'upload'|'download', entryId, expiresAt }` query grants. Upload/download routes require the matching unexpired grant and entry state; use a generic 401 response on malformed, expired, or mismatched grants.
   - Add `apps/control-plane/src/cache/routes.ts` and register it in `apps/control-plane/src/http/app.ts:createControlPlaneApp` before static routes. Implement JSON Twirp POST routes exactly at `/twirp/github.actions.results.api.v1.CacheService/CreateCacheEntry`, `/FinalizeCacheEntryUpload`, and `/GetCacheEntryDownloadURL`, with GitHub field names `signed_upload_url`, `signed_download_url`, `matched_key`, `size_bytes`, and `entry_id`. Return Twirp JSON errors `{ code, msg, meta }`; accept `application/json` only because current first-party `@actions/cache` v2 clients use the generated JSON client. Legacy v1 and protobuf requests are not reimplemented; the guest proxy forwards them to GitHub.
   - `CreateCacheEntry` chooses the first token scope with `Permission >= 2`, atomically reserves metadata, begins the backend upload, and returns `{ ok:false }` for an immutable-key or active-upload conflict. Its signed URL is `${PUBLIC_BASE_URL}/api/cache/uploads/:entryId?grant=...`.
   - The upload endpoint implements Azure Block Blob's `PUT ?comp=block&blockid=...` and `PUT ?comp=blocklist`: stream blocks to `putPart`, parse the XML `<BlockList><Latest>…</Latest></BlockList>` without accepting external entities, require every declared block to exist exactly once, complete the backend upload, and move metadata to `blob_ready`. Include `x-ms-request-id` and `201` responses expected by the Azure SDK.
   - `FinalizeCacheEntryUpload` requires a write scope matching the reserved entry, verifies key/version/repository/scope and the declared size against the committed object, then atomically moves it to `ready`; repeated identical finalize calls return the same entry ID, while mismatches return a Twirp failed-precondition error. `GetCacheEntryDownloadURL` applies the ordered match algorithm, verifies the object still exists before promising a hit, self-heals dangling metadata by marking it for deletion and retrying the remaining candidates, and returns `{ ok:false }` for a true miss.

5. **Intercept only GitHub's cache RPCs inside each ephemeral job using Bun/TypeScript.**
   - Add the pure-JavaScript `selfsigned` dependency to `apps/job-agent/package.json` and create `apps/job-agent/src/cache-proxy.ts` with `startCacheProxy(config): Promise<{ env: Record<string,string>; close(): Promise<void> }>` implemented with Bun-compatible `node:net`, `node:tls`, `node:http`, and `node:https`. Generate a fresh per-job self-signed certificate/private key for the exact configured results host; retain the private key only in the job-agent process and delete certificate files on close.
   - Expose a loopback HTTP CONNECT proxy through `HTTP_PROXY`/`HTTPS_PROXY`. Tunnel every non-target hostname byte-for-byte. For the exact results host, terminate TLS using the ephemeral certificate, route only the three exact cache Twirp paths to `cacheBaseUrl` while preserving method, body, `Authorization`, and content type, and forward every other results-service path to the original GitHub origin. Strip hop-by-hop headers and never log authorization, grants, signed URLs, bodies, or JIT configuration.
   - Trust the ephemeral certificate only inside the disposable job: set `NODE_EXTRA_CA_CERTS` for bundled Node actions; on Linux/macOS construct a private CA bundle from the platform bundle plus the ephemeral certificate and point `SSL_CERT_FILE` at it; on Windows add/remove the certificate in the current disposable machine root store with `certutil.exe`. This is trust configuration around the untouched official runner, not a new .NET component.
   - Fail open before runner launch: if certificate generation, trust setup, or proxy binding fails, emit one redacted warning and launch the runner without proxy variables so GitHub cache remains in use. Once active, if the Whitesmith control-plane call throws or returns 401, 403, 429, or 5xx before a Twirp response is accepted, replay that small buffered Twirp request once to the original GitHub origin. Do not fallback after Whitesmith has returned a successful create/finalize/lookup response; data-plane failures remain ordinary cache save/restore failures and expired uploads are cleaned later.

6. **Carry proxy configuration through every existing runtime without changing runner binaries.**
   - Update `apps/orchestrator/src/lease-lifecycle.ts` and `apps/orchestrator/src/mac-agent.ts` to copy `bootstrap.cacheProxy` into `RuntimeDriver.createLease`, then update `apps/orchestrator/src/kata-k3s.ts`, `hyperv.ts`, and `windows-container.ts` to include the optional property in their protected `bootstrap.json` rather than reconstructing only the old four fields. Update their contract tests to prove the URL is present only when configured and that the encrypted dispatch payload still contains no plaintext cache/storage credential.
   - Refactor `apps/job-agent/src/bootstrap.ts` so both `consumeJitConfig` and `consumeGuestJitConfig` call one `runRunnerWithOptionalCache(encodedJitConfig, runnerRoot, platform, cacheProxy)` helper: start the proxy, merge only its returned environment into the runner process, await runner exit, and always close the proxy/remove trust in `finally`. Extend the private `GuestBootstrap` parser to accept the optional config and reject malformed mixed fields before launching the runner.
   - Update Tart's `apps/orchestrator/src/tart.ts:TartVmRuntime.startWithBootstrap` to receive the full `Lease`, mount/copy a versioned `bootstrap.json` instead of only `jit-config`, and invoke the job agent through the same bootstrap-consuming path with completion mode `exit`. Preserve the current Tart VM start, log streaming, completion, and cleanup behavior. This gives Linux Kata, Windows Hyper-V/container, and macOS Tart the same interception behavior in the first release.

7. **Wire deployment settings and observable smoke coverage.**
   - In `apps/control-plane/src/index.ts`, build/probe the configured cache service, pass it into `ControlPlaneHttpDeps`, register cache cleanup with the existing retention tick, and pass only public proxy configuration into job reconciliation. Add a non-secret cache status (`off`, `local`, or `s3`, plus last cleanup failure) to `/api/healthz`; cache degradation does not make the main control plane unready because jobs fail open to GitHub before interception.
   - In `deploy/control-plane/compose.yaml`, set production default `WHITESMITH_CACHE_STORAGE=${WHITESMITH_CACHE_STORAGE:-local}`, `WHITESMITH_CACHE_LOCAL_ROOT=/var/lib/whitesmith/cache`, and pass through S3 endpoint/region/bucket/path-style plus standard AWS credential variables. The existing `whitesmith-data` volume persists local archives. In root `compose.yaml`, add a profile-gated MinIO service and one-shot bucket initializer for the S3 integration test; do not add MinIO to production compose.
   - Add manual-only `.github/workflows/cache-smoke.yml` with `cache-key` and `expect-hit` inputs. It runs on a Whitesmith label, uses unmodified `actions/cache@v5`, caches `.cache-smoke`, asserts the requested hit/miss through `steps.cache.outputs.cache-hit`, creates a known payload on a miss, and verifies that payload after a hit. Add `tests/live-cache-smoke.ts` to dispatch one unique-key miss run followed by one same-key hit run, wait for both successful reaped leases using the existing live-smoke helpers, and assert one ready cache row/object for the repository.

## Critical files & anchors
- `packages/contracts/src/orchestration.ts:LeaseBootstrapEnvelope` — encrypted control-plane-to-worker boundary that must carry only public cache proxy configuration.
- `packages/db/src/index.ts:migrations` — checksum-protected migration sequence; add version 10 without altering versions 1–9.
- `apps/control-plane/src/http/app.ts:createControlPlaneApp` — cache Twirp/data routes must precede the SPA fallback and use runtime-token/grant auth, never dashboard sessions.
- `apps/job-agent/src/bootstrap.ts:consumeJitConfig` / `consumeGuestJitConfig` — single runner-launch boundary where proxy variables can be applied without modifying the official runner.
- `apps/orchestrator/src/tart.ts:TartVmRuntime.startWithBootstrap` — unlike the other drivers, Tart currently transports only the JIT string and must move to the shared versioned bootstrap envelope.

Repeat once with local storage and once with the MinIO S3 configuration.

## Assumptions & contingencies
- Scope is current GitHub.com cache service v2 JSON used by first-party `actions/cache@v5`; legacy v1 and protobuf cache clients continue to GitHub through the proxy. If the current first-party package switches to protobuf during implementation, add protobuf decoding/encoding for the same three messages behind the existing handlers rather than changing storage or matching semantics.
- The control plane's public origin accepts 64 MiB request bodies and streaming responses. If the deployed edge has a lower request limit, set `PUBLIC_BASE_URL` for cache traffic to a direct control-plane origin that satisfies that limit; do not buffer/rechunk blocks or expose S3 credentials to jobs.
- The official results hostname defaults to `results-receiver.actions.githubusercontent.com`. If a live job uses another host, capture only that hostname from redacted proxy diagnostics, configure `WHITESMITH_CACHE_RESULTS_HOST` to it, and keep all nonmatching hosts tunneled to GitHub.
- S3-compatible stores must implement AWS multipart upload and SigV4 presigned GET. Providers lacking either capability are unsupported; use the local backend rather than adding provider-specific fallbacks.
